# W1b 计划：补视角（2026-10-12）

依据 `docs/hand_gate_w1c_result.md`。一句话：**W1c 证明换规则救不回弃权，
而按视角分组后 `n>=3` 是唯一能在零泄漏下放行 OWNER 的子集（23.5%，对全量 0.0%）。
W1b 就是去检验这是因果还是选择。**

所有产物进 `video-split`（研究仓库），**不进 Long_Video_Splitting** ——
那里只放会改变流水线的东西。

---

## §0 先回答一个问题，否则 W1b 可能根本做不了

设置是 `frames_per_track = 5`，而实测视角数是 `{1:68, 2:69, 3:33, 4:7}`。
**在动手补之前必须知道为什么少。** 从 `three_probe.items_for(...)` 看，
视角是对轨迹的行做「均匀时间采样 + 两端必取」之后、再过 `min_px` 过滤得到的，
所以 `n < 5` 只有三个可能来源：

```
① 轨迹本身不足 5 行（短轨迹）
② 行被 min_px 滤掉（框太小）
③ 裁剪/取帧失败
```

**这三种的后果完全不同：**

- 若 ① 是主因 → 那些轨迹**没有第三个视角可补**，W1b-1 不可行，
  杠杆只剩放宽 `min_px`，而那有自己的代价（见 §3）。
- 若 ② 是主因 → 放宽**只用于视角**的 `min_px` 是一个便宜且定向的改动。
- 若 ③ 非零 → 那是工程缺陷，归到 W2，不该混进这里算收益。

### W1b-0：逐轨迹的视角预算普查（必须第一步）

把 gate 输出和 stage-3 的轨迹行 join，对那 137 条 `n<=2` 的轨迹报：

```
总行数  /  过 min_px 的行数  /  框宽分布（中位、最小）/  实际取到的视角数
```

**产出一张表就够了，不需要任何模型调用。** 需要的是服务器上那 10 条录像的
stage-3 轨迹输出（gate csv 里只有视角数 `n`，没有帧数和框宽）。

**判据（事前）：**
```
n<=2 的轨迹里，>=60% 有 3 行以上过 min_px        → 走 W1b-1（纯重采样）
>=60% 的轨迹总行数就 <3                         → W1b-1 不可行，走 §3 评估 min_px
两者都不占多数                                  → 分两组分别处理，分别报收益
```

**这一步同时解掉 W1c 留下的那个未检验混淆**：它会给出每条轨迹的长度，
于是「`n>=3` 的优势是不是只因为轨迹更长」可以用观察性对照先看一眼
（虽然因果检验仍然是 W1b-1 本身）。

## §1 W1b-1：重采样（若 §0 判据指向 ①② 之外）

对 `n<=2` 的轨迹把视角提到 **4**（不是 3——3 是可分性出现的下界，取 4 留一个余量），
重跑 context 判定。

**配对设计**：同一批轨迹、同一个 gold、只改视角数。这是 within-track 比较，
比任何跨子集比较都强。

**硬规则**：`视图数不许减` —— 这次是**往上加**，方向正确。
`frames_per_track` 与 `min_views` 不是优化对象。

**要一起报的，否则结论会被追问：**

- **新增视角的系统性差异。** 补进来的帧在时间上更靠中间（两端已被必取），
  框可能更小。**报补充前后的框宽分布与时间位置分布。** 如果新视角系统性更小，
  那么「补视角」和「放宽 min_px」在效果上会混在一起。
- **describe 那一遍的成本。** 它占 89.9% 墙钟、慢 3.4 倍，而且
  `owner-gate-barely-beats-majority` 已测到它值 +12.0 pp OWNER 放行率
  （CI [+5.7, +16.7]），**所以不能为省钱砍掉它**。成本要按「带描述」算。

**事前判据（按录像聚类 bootstrap，4000 次）：**
```
零泄漏下 OWNER 放行率显著 > 0                    → W1b 成立，继续 W4 验证
放行率上去但护栏同时恶化                          → 报成取舍曲线，由使用方选操作点，
                                                  不默认采纳
补到 4 视角后仍不可分（像现在的 n=2）             → **不是视角数的问题**：
                                                  这个分数在短轨迹上没有信息，
                                                  整个 gate 路线要重估
```

最后那一条是真正的分叉点，而且它比前两条更有信息 ——
它会把问题从「怎么调这个门」变成「这个门该不该存在」。

## §2 成本估算（为什么这件事值得做）

```
n<=2 的轨迹   137 条 / 177 条可评分 = 77%
每条从 2 加到 4 视角 → 额外 274 个视角前向
每个视角两遍模型：约 60 token 描述 + 1 个 token 的 logits
```

对照已测的整链 **184 秒/录像**（10 条 / 6 卡），其中 stage 1 检测含 hand-ness
占 83.5 秒/条。context 判定不在那条链里（它是 gate 阶段），
**所以 W1b 的增量不是 184 秒的倍数，而是 gate 阶段的增量**，
而 gate 阶段的成本本来就由 describe 主导。

→ **W1b-0 的那张表要同时给出 gate 阶段当前的视角总数**，这样增量可以写成
「视角数从 X 变成 Y，成本按 describe 的单视角耗时线性外推」，而不是一个猜测。

## §3 若 §0 指向 min_px：这条路要先付一次测量

放宽 `min_px` 会把小框带进视角。已知的三件事让这件事不能直接做：

```
小框藏着一半的非手      <150px 非手率 12.2%  对  >=150px 的 5.9%，小框占 32.7%
hand-ness 在小框上崩    246px 框上判非手 40/40 = 100%，23-28px 上只有 5.5% 且无阈值可救
30-100px 从未测过       而别人的手中位恰好 87px
```

**所以 §3 的前置条件是一次测量不是一次训练**：在 **30-100px** 这一带测 hand-ness
的可用性。这一带是别人的手的中位所在，也是放宽 min_px 后新视角会落入的区间。

**判据：** 这一带上 hand-ness 可用（有一个阈值同时达到可接受的精度与召回）
→ 放宽 min_px 只用于视角；不可用 → 这条路关闭，不要靠「反正是只用于视角」
说服自己。

## §4 执行顺序与基础设施

```
W1b-0  视角预算普查        无模型调用，需服务器上 stage-3 的轨迹输出     ← 先做
  └─ 判据分流
W1b-1  重采样到 4 视角     需服务器 GPU；配对；带描述
  或
W1b-2  30-100px hand-ness 测量 → 再决定 min_px
W2     覆盖缺口 + 轨迹数不变量检查（21% 从未被看到，与此并行）
W4     冻结验证 20-30 条   所有数字的 n=10 上限只有它能解
```

**基础设施提醒（已踩过）：**
- 服务器上**没有 repo checkout**（今天 `find` 确认过），代码要走 **git bundle**；
  `git pull` GitHub 在那台机上必失败，不要重试。
- 路由是堡垒机：`ssh sixiang-dev`，**不是裸 IP**（我为此误报过两次「服务器连不上」）。
- 等待一律等产物 + 停滞超时，**不许用 `pgrep`**。
- 远端杀进程分两步：先列 PID，再单独 kill。
- 大文件只放 SAN（`/data/storage/docker`），跑前 `df -h`。

## §5 这一步能改变什么

W1c 之后，「work」这个目标的全部希望压在 W1b 上：

```
分类器      96.6%（274 条 gold）      已经够好，不是瓶颈
判错         6/75 = 8%                 分类器的全部责任
弃权        34/75 = 45%                W1c 证明换规则救不回
没跑到       9/75 = 12%                W2 的工程缺陷
```

**弃权那 45% 只有一条路：把证据补上。** 若 W1b 成立，
`n>=3` 的 23.5%（零泄漏）与 58.8%（≤15% 护栏）是可期望的量级，
而当前全量是 0.0% 与 27.3%。若 W1b 不成立，那就得到一个更强的结论 ——
**这个分数在短轨迹上没有信息，而 77% 的轨迹是短的**，
于是「整轨免打码」这个产品形态本身要重新设计，而不是继续调门。
