# 留出集第一条：开发集结论没有迁移过去（2026-10-12）

窗口值在看这条录像之前就冻结在 150 帧（`a539d89`），所以这是一次真正的留出测试。

---

## §1 事前承诺的那个对比

```
R26_0825_100512   该接 8 处
  窗口  30（旧值）    接对 3    接错 0
  窗口 150（冻结值）  接对 2    接错 0      <- 比旧值差
```

**方向是负的。**

## §2 事后诊断（不用于改值）

不是「150 在台地里选错了」，是**整个台地都失败**：

| 窗口 | 接对 | 接错 |
|---|---|---|
| **30** | **3** | 0 |
| 40 / 50 / 60 | 2 | **1** |
| 80 | 2 | **2** |
| 100 / 150 | 2 | 0 |

机制：`100512` 是目前碎片化最密的一条 —— **2 只手 18 条轨迹**。
窗口放宽让候选数从 3 涨到 6，「恰好一个候选」更难满足，于是规则弃权更多。
窗口 30 下接上的 `A 5→7`、`B 6→8`，在 150 下都变成多候选被放弃。

这与开发集上观察到的非单调性是同一个机制，只是在这条录像上它压过了收益。

## §3 现在不改值

1 条录像 / 8 个事件，对 7 条录像 / 23 个事件。**n 太小，不足以推翻**，
但方向一致为负，不能当噪声忽略。

拿一条留出录像回头调参，正是留出集存在的意义所要防的事
（这个项目为同类做法付过三次代价：选片 proxy r=−0.46、HAL 阈值、Driver A 门）。

## §4 判决规则 —— 在剩下两条标注之前写死

留出集 = `143303` / `100512` / `063732`，三条**全部**标完后一次性判决：

```
设 Δ接对 = (150 的接对总数) − (30 的接对总数)，Δ接错同理，三条合计。

  Δ接对 > 0 且 Δ接错 <= 0     -> 保留 150，开发集结论迁移成立
  Δ接对 <= 0 或 Δ接错 > 0     -> **回退到 30**，并记下「开发集结论未迁移」
                                 —— 不是再挑一个新值，那是把留出集变成开发集
```

无论哪个结果，§4 里「按秒写、由实测 fps 换算」那个改法都保留：
它修的是一个算错 5 倍的换算，不依赖任何 gold。
回退的意思是 `WINDOW_SECONDS = 1.0`（= 30 帧，现状），不是变回写死的帧数。

**不允许的做法**：看完三条之后在 50/60/80/100 里挑一个在留出集上最好的。
那条曲线在开发集上已经被证明非单调，在留出集上又换了形状，
在两边都挑一遍等于两边都过拟合。

## §5 这一条本身的逐手指标

```
100512  A  17 帧  3 条轨迹  94.1%  2 切换   手画 1/17
100512  B  10 帧  4 条轨迹  80.0%  3 切换   手画 2/10
主指标 0/2
```

两只手覆盖都不低（94.1% / 80.0%）却都碎成 3-4 条 —— 典型的**纯关联失败**，
检测没问题。这也是为什么这条录像对窗口这么敏感。

注意 `present_rate = 0.55`，是全部十条里最低的：40 格网格只有 22 帧有图。
所以这条的覆盖率上界最松，读数要带着这个折扣。

# 留出集第二条：方向相反（2026-10-12）

```
R26_0826_063732   该接 9 处
  窗口  30（旧值）    接对 1    接错 0
  窗口 150（冻结值）  接对 3    接错 0      <- 比旧值好
```

**与第一条方向相反。**

## 两条合计（判决仍不发）

| 窗口 | 该接 | 接对 | 接错 |
|---|---|---|---|
| 30 | 17 | 4 | 0 |
| 150 | 17 | **5** | 0 |

Δ接对 = **+1**，Δ接错 = 0。按判决规则这会算「保留 150」，
**但 143303 还没标，规则写的是三条一起判一次，所以现在不发判决。**

## 为什么这两条相反，不是噪声

两条都是候选密集的录像，但密集的方式不同：

- `100512`：18 条轨迹 / 2 只手。窗口放宽让候选从 3 涨到 6，
  原本「恰好一个候选」的两处（A 5→7、B 6→8）变成多候选 → **丢了 2 处**。
- `063732`：19 条轨迹 / 2 只手。窗口 150 下候选数涨到 **9-10 个**，
  几乎所有端点都变歧义 —— 但它在窗口 30 下接对数本来就只有 1，
  被窗口卡住的那两处（A 15→18 间隔 48、B 16→17）一放宽就接上了，**净 +2**。

也就是说：**窗口放宽的净效果 = 解锁「被间隔卡住」的 − 损失「本来唯一候选」的**，
两项都随候选密度上升，哪一项大取决于这条录像里两类事件各有多少。
这正是开发集上那条非单调曲线的机制，只是在录像之间表现为方向翻转。

**后果**：两条方向相反意味着第三条基本上会单独决定判决结果。
那是个很弱的基础，判决出来之后要把这一点写在结论里，
不管方向如何 —— 「3 条录像里 2:1」不是一个可以部署的证据强度。

## 逐手指标（两条留出）

```
100512  A  17帧  3条  94.1%  2切换   手画 1/17
100512  B  10帧  4条  80.0%  3切换   手画 2/10
063732  A  31帧  4条  87.1%  3切换   手画 10/31
063732  B  32帧  6条  90.6%  5切换   手画 4/32
主指标 0/4
```

四只手覆盖都在 80% 以上却全部碎成 3-6 条 —— **纯关联失败**。

`063732` 手 A 的 530-610 连着 **9 个手画 anchor**：检测器在那一整段漏掉这只手。

## 「覆盖率 = 1−手画率」现在是 14/17，不再接近恒等

九条 / 17 只露面的手里，三只例外：

| 手 | 偏差 | 读法 |
|---|---|---|
| 133848 B | +5.4 点 | 几帧标注者画了框，但确实有轨迹盖住 |
| 063732 B | +3.1 点 | 同上 |
| **063732 A** | **+19.4 点** | 手画 32.3% 而覆盖 87.1% —— 有 6 帧检测存在但位置差到标注者宁可自己画 |

所以之前那句「覆盖率基本是检测指标」要收窄：
**它主要由检测漏报决定，但「检测到了而框得很差」是一个独立的、可以很大的第三项。**
063732 手 A 那 19.4 点全是这一类。

不变的是另一条：**17 只手里 n_tids==1 的 4 只覆盖率全是 100%**，
所以主指标的四个阈值仍然给出同一个数字，「覆盖 >= X」这个合取项仍然从没起过作用。

# 判决（2026-10-12）：规则通过，但通过的幅度是 19 处里的 1 处

第三条 `143303` 标完，按 `146fbed` 事前写死的规则一次性判决。

## §1 三条合计

| 窗口 | 该接 | 接对 | 接错 |
|---|---|---|---|
| 30（旧值） | 19 | 6 | 0 |
| **150（冻结值）** | 19 | **7** | 0 |

**Δ接对 = +1 > 0，Δ接错 = 0 <= 0 → 按规则：保留 150。**

## §2 但拆开看，这个 +1 几乎没有支撑

| 录像 | 该接 | 30 接对 | 150 接对 | Δ | 轨迹数 |
|---|---|---|---|---|---|
| `143303` | 2 | 2 | 2 | **+0** | 4 |
| `100512` | 8 | 3 | 2 | **−1** | 18 |
| `063732` | 9 | 1 | 3 | **+2** | 19 |

**一正、一负、一中性。** 不是「3 条里 2:1」，是 1:1:1 —— 比我在
`d5c66a6` 里预警的还弱。

`143303` 对这次比较**零贡献**：它只有 4 条轨迹、2 处该接，而且两处在
两个窗口下都接上了。它是十条里最干净的一条，所以也最没有区分力。

于是判决实际上建立在两条方向相反的录像上：`100512` 的 −1 和 `063732` 的 +2。
净 +1，而总事件数是 19。

## §3 所以结论要这样写

**按规则保留 150，但不是因为留出集支持它。**

留出集给出的是「分不出来」：三条录像一正一负一平，净差一处接合。
真正支撑这个改动的仍然是 §4 那个与 gold 无关的理由 ——
`WINDOW = 30` 的注释声称是 5 秒而实际是 1 秒，换算错了 5 倍。
**修一个算错的换算不需要留出集同意，而留出集也确实没有反对。**

不做的事：
- 不因为 `100512` 的 −1 回退（那是拿一条留出录像调参）
- 不在 50/60/80/100 里另挑一个（事前明文禁止，两边各挑一遍等于两边过拟合）
- **不把这次结果当作「窗口改对了」的证据**。它只支持「没改坏」。

## §4 这次测量真正确立的，不是窗口

十条录像 / 19 只露面的手，合起来：

```
主指标（单一轨迹 且 覆盖 >= X）
  >= 50%   31.6%   (6 / 19)
  >= 80%   31.6%   (6 / 19)
  >= 90%   31.6%   (6 / 19)
  >= 95%   26.3%   (5 / 19)
轨迹数中位 2.0（理想 1）；切换中位 2.0（理想 0）
```

**近七成的手不是由单一轨迹持有的**，而窗口在 19 处该接里只动了 1 处。
也就是说：**窗口从来不是这条线的瓶颈**，它只是第一个被量出来的参数。

开发集上已经分好的类仍然成立，而且在留出集上重复出现：
窗口能解锁的是「被间隔卡住」那一类，而大头是
**两只手的碎片在空间上交织 → 两端面对同一组候选 → 规则弃权**，
以及 **tracker 把一只手同时放成两条重叠轨迹**（merge-only 结构上修不了）。

下一步应该针对的是这两类，不是继续调窗口。

## §5 顺带：主指标的阈值第一次起作用了

`143303` 手 A 是十条里**第一只「单一轨迹但覆盖不满」的手**（1 条轨迹 / 93.8%），
所以 >=95% 这一档第一次与其它三档分开（5/19 vs 6/19）。

它的覆盖率 93.8% 精确等于 1 − 手画率（2/32 = 6.25%），
所以这一档之差量的仍然是**检测漏了两帧**，不是关联出了问题。

这反而更清楚地说明：**把「单一轨迹」和「覆盖 >= X」合成一个数是错的**，
因为合取里两项量的是不同的东西，而且阈值一旦起作用，起的作用来自检测那一项。
