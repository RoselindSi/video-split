## §1 Step 0：那 47 个点的去向，预测命中

完整复现 README 的总体：**202 条可评分 / 10 条录像 / 75 OWNER / 127 OTHER**。
被误糊的 OWNER 拆开（三条臂）：

| | unsure（弃权） | 没跑到 | 判成 other | 合计 |
|---|---|---|---|---|
| corpus_0 | 34 | 13 | **6** | 53 |
| corpus_1 | 30 | 9 | **6** | 45 |
| corpus_2 | 37 | 6 | **6** | 49 |

事前写下的预测是「`unsure` 最大，`没跑到` 次之，`判成 other` 最小且 ≤6」。
**`other` 在三条臂上都恰好是 6** —— 它来自分类器，各臂几乎相同。

```
75 条 OWNER 里：判错 6 (8%)   弃权 34 (45%)   没跑到 9 (12%)   放行 26 (35%)
```

**分类器只负责 8%。** 计划的核心前提成立。

（这三条臂都没复现 README 的 49.3%/37.3%，给的是 29.3/40.0/34.7%，
所以 README 那一对具体是哪两个目录仍未认出。但分解结构三条臂一致，
结论不依赖于认出它。）

## §2 W1c：换阈值救不回弃权 —— 规则已经在可达前沿上

把弃权换成「用现有分数强行判定」，扫六个分数列的全部阈值
（分母是那 10 条录像内的全部 gold，**含没跑到的**，因为部署里它们也会被打码）：

```
            护栏<=0%   5%     10%    15%    20%
p_median      0.0%   14.6%  20.7%  35.4%  41.5%
p_max         0.0%   14.6%  20.7%  29.3%  45.1%
p_min         0.0%   11.0%  18.3%  35.4%  37.8%
positive_frac 0.0%    0.0%   0.0%   0.0%  37.8%
base_p_median 0.0%    0.0%  18.3%  31.7%  36.6%
base_strong   0.0%    0.0%  18.3%  32.9%  39.0%

现在的规则操作点：OWNER 放行 36.6%   别人的手被放行 16.9%
```

**规则（36.6% @ 16.9%）基本就落在前沿上** —— 同等护栏下最好的阈值给 35.4%。
**所以「弃权白白损失了可用性」是错的：弃权掉的那些轨迹，分数里本来就没有
可以用来救它们的信息。**

### 零泄漏为什么全是 0.0%：顶端不可分，而且不是一条异常

```
别人的手 p_median >= 0.999 的：18 条 / 111
最高的那条 0.999992，高于全部 66 条自己的手（0 条超过它）
那 18 条的 reason 几乎全是 too_few_base_track_consensus，n=1 或 2
```

**分数在顶端饱和且失准：模型在 1-2 个视角上给出极度自信的错误判断。**
所以任何单调阈值都做不到「零泄漏且放行非零」。

## §3 机制：视角被饿死，而且这一条是可操作的

```
视角数 n 的分布：{1: 68, 2: 69, 3: 33, 4: 7}      ← 77% 的轨迹只有 <=2 个视角
而设置是 frames_per_track = 5
129 条 unsure 里 128 条的 reason 是 too_few_context_views
```

按视角数分组重扫，分数的行为完全不同：

| 子集 | OWN | OTH | 护栏≤0% | 5% | 10% | 15% | 20% |
|---|---|---|---|---|---|---|---|
| 全部 | 66 | 111 | **0.0%** | 16.7% | 21.2% | 27.3% | 50.0% |
| n=1 | 22 | 46 | 0.0% | 4.5% | 4.5% | 9.1% | 27.3% |
| n=2 | 27 | 42 | 0.0% | 11.1% | 29.6% | 40.7% | 44.4% |
| **n≥3** | 17 | 23 | **23.5%** | 23.5% | 29.4% | **58.8%** | 58.8% |

`p_median` 的中位数说明了为什么：

```
n=1    OWNER 0.7788   OTHER 0.0006
n=2    OWNER 0.5000   OTHER 0.0028     ← 两个视角一正一负，完全无信息
n>=3   OWNER 0.9987   OTHER 0.0015     ← 可分性出现
```

**`n>=3` 是唯一能在零泄漏下放行 OWNER 的子集（23.5%），
而在 ≤15% 护栏下它给 58.8%，对全量的 27.3%。**

## §4 必须写下的三条限制

**① `n>=3` 只有 17 OWNER / 23 OTHER，23.5% 就是 4/17。** 样本极小。

**② 选择效应未检验，而且用手上的数据测不了。**
拿到 ≥3 视角的轨迹可能本来就更长更清楚，那么「给所有轨迹 3+ 视角」不会自动
迁移。要控它需要轨迹长度，而：`gold_b*.csv` 的 `frames` 列**是空的**
（那批表没填）；gate csv 只有视角数 `n` 没有帧数；服务器上
`ship8/*.csv` 是逐帧的但**没有 tid 列**，映射不到轨迹。

→ **这个混淆的检验就是 W1b 本身**：对 `n<=2` 的轨迹强行补视角到 3+，
看它们是否表现得像现在的 `n>=3` 组。那是因果检验，比我能从现有文件里
搭出来的任何观察性对照都强。

**③ 覆盖缺口比 Step 0 的口径显示的更大。**
那 10 条录像内有 224 条 gold，而 run 里只有 177 条 —— **47 条（21%）从未被看到**。
`against_gold` 用 `gold ∩ run` 做 keys，所以这 47 条在它的分母里不出现。
两个分母都要报，差额就是覆盖缺口。

## §5 计划更新

```
W1a 整轨多数票     ✗ 取消 —— 规则已在前沿，换聚合方式救不回弃权
W1c 阈值曲线       ✓ 已完成，结论是否定的（但它定位了 W1b）
W1b 补视角         ← 现在是整个计划。已有量化预测：
                     n<=2 的 137 条轨迹补到 3+ 视角后，应当表现得像现在的 n>=3 组
W2  覆盖缺口       ← 21% 从未被看到，比原估计大；加轨迹数不变量检查
W3  低分框只续接   ← 不变，放最后
W4  冻结验证       ← 不变，n=10 是所有这些数字的硬上限
```

**W1b 的成本是可估的**：只对 `n<=2` 的轨迹加采样，占 77%，每条从 2 加到 4 个视角，
所以额外前向约等于当前 context 判定的 0.77 × 1 倍，而不是全量翻倍。
**而「视图数不许减」这条硬规则正好说明方向是对的** —— 这次是往上加。

**事前判据：**
```
n<=2 组补到 3+ 后，零泄漏下 OWNER 放行率显著 > 0            → W1b 成立
补到 3+ 后它们仍然不可分（像现在的 n=2）                    → 不是视角数的问题，
                                                           是这个分数本身在短轨迹上
                                                           没有信息；整个 gate 路线要重估
放行率上去但护栏同时恶化                                    → 报成取舍曲线，不默认采纳
```
