# B2 拍摄说明（给拍摄者）

判据在 `branching_pilot_b2_spec.md`，冻结于 2026-09-28，这份文件不改它，只把它
翻译成拍摄时能照着做的动作。

**这一批只有 10–20 条，所以一条拍废就是 5–10% 的产出。** 下面每一条"不要"都对应
一次已经发生过的零产出。

---

## 一句话要的是什么

> **同一个可观察状态，在同一条录像里反复出现，每次根据当时的条件进入不同的后续。**

```
          看一下这个东西
          ├─ 是甲类 → 放 A
          ├─ 是乙类 → 放 B
          └─ 拿不准 → 再看一次
          ↑
      然后回到这里，再来一个东西
```

关键是那个**回到这里**。没有"回到"，就没有分叉。

## 为什么不能拍"看起来有分支"的复杂任务

```
拧盖 → 擦净 → 装箱 → 贴标 → 收工
```

这一串有五个不同动作，任务也不简单，但每个状态只有一个后继，**产出是 0**。
上一批 15 段精选录像就是这个形状：96 个决策点，0 个分叉。

要的不是动作多，是**同一个点上有选择**。

---

## 四种任务，按好拍程度排

### 1. 分拣（最推荐）

一堆混在一起的东西，一件一件看，按类别去不同去处。

- 去处至少 3 个，其中一个是"拿不准 / 再看一次"
- **至少 12–15 件**，而且类别要交替出现，不要甲类全放完再放乙类
- 东西本身要能在画面里看出类别差异（颜色、形状、标识），不能靠拍摄者脑子里知道

例：回收分拣、零件按规格分箱、快递按区域分堆、衣物按材质分篮。

### 2. 排障 / 检查后决定

逐个检查部件，按状态决定处置。

- 处置至少 3 种：拧紧 / 更换 / 继续检查
- 同一类部件要检查**多次**，且至少两次得出不同处置
- 部件状态要在画面里可见（松了、裂了、脏了）

### 3. 复杂料理

反复查看锅里的状态，按状态决定下一步。

- 下一步至少 3 种：继续加热 / 加料 / 起锅
- **查看动作要重复多次**，这是这类任务唯一的分叉来源
- 别按菜谱固定顺序走，那又变成单后继链

### 4. 中断式流程

做主任务时被打断，按打断类型决定应对。

- 最难控制，打断容易显得是演的
- 只在自然会被打断的真实场景里拍

---

## 三条硬约束（判据二、三的落地）

### ① 分叉必须由画面里能看见的条件决定

**可以**：这件是玻璃瓶所以去 A，那件是外卖盒所以去 B。
**不可以**：上次放了 A，这次故意放 B 换个花样。

人为随机换路线，即使最后图有用，也说明不了它对应真实的推理 —— 等于白拍。

### ② 每个分叉要能说出原因

拍完一条，对每个分叉写一句为什么，粗标页面会在当场追问（标完刚那一段就问，
不回头问，因为回头想出来的理由不能用）。

写不出原因的分叉，在统计里单独计数、不进"由可观察条件驱动"那一项。

### ③ 手要看得见

**≥100px 的手框出现在 ≥60% 的帧里**，拍完用这条验：

```bash
python -m src.auditor.boundary.branch_hand_check --floors 60 100
```

**不要用裸检测率自己判断** —— 它在上一批数据上把最差的一条排到了第一名
（那条检测率 55% 最高，但手框只有 30px 宽）。

---

## 不要拍的

| | 为什么 |
|---|---|
| 固定顺序的重复操作（拧盖 ×20、装手机壳 ×20） | 当前数据里绝大多数是这个形态，产出恒为 0 |
| 一次只做一件事、做完就结束 | 没有"回到同一个点" |
| 分支由拍摄者临时决定 | 违反约束① |
| 手大部分时间在画面外或很小 | 过不了手部可见度 |
| 单条超过 3 分钟 | 标注单位上限；长的就拆，但每一段都要自己满足"回到同一点" |

---

## 交付与判定

1. 单条 ≤ 3 分钟，10–20 条
2. 跑 `branch_hand_check --floors 60 100`，不过的不要进标注
3. 用 `b2_coarse_page.html` 粗标：只标**状态序列**和**分叉原因**，不做 object /
   action / result / cluster / confidence 那一整套
4. 跑判定：

```bash
python -m src.auditor.boundary.b2_yield --export r1_B2_coarse.json --out b2_yield.json
```

它直接打印 GO / NO-GO / BORDERLINE。**判据在看到数据之前就写进代码了**，
所以这一步没有可商量的余地 —— 这是这份 spec 的设计目的，不是它的副作用。

### 判据（原文照抄，不在这里重述成别的话）

- ≥ 15–20 个真正 prefix-valid 的 G-branch 决策
- 来自多条独立录像，不能全由一条异常高分支的录像贡献
- 产出率 ≥ 0.5–1 个 / 录像
- 并且至少一部分分支由可观察条件驱动

**No-Go 是硬的**：刻意选了 branching-native 任务之后仍只有个位数，就停掉
Graph 作为主方法方向。不是"再拍 20 条看看"。

---

## 标注者要注意的一件事

粗标只有一个要求，但它是整个合同里最容易漂的那一条：

> **回到之前做过的那件事，用同一个代号。**

不是"看起来像"就用同一个，也不是每次都新建一个。代号漂了，出度就全是 1，
拍得再好也白费。这一批的目的之一就是先把这条单独练出来。
