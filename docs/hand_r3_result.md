# R3 结果：>2 只手不是模型错误，是整轨裁决覆盖了逐帧封顶（2026-10-12）

工具 `src/semhand/own_track_cleanup.py`，数据 `/workspace/e2e_v4`（10 条录像）。

---

## §1 ①清理短且冗余的 own 轨迹：便宜、正确、但解决不了主要问题

规则是 **短（<10 帧）且冗余（≥80% 的帧已被别的 own 轨迹覆盖）**。
「冗余」这一条不是修饰：

```
own 轨迹数 中位    6.5  ->  5.0
own 轨迹数 合计     61  ->  55（丢 6 条）
own 覆盖帧        3245  -> 3245（损失 0.00%）
>2 只手的帧         52  ->   48（只降 8%）
恰好 2 条的录像       2  ->    2 / 10（没变）
```

**另有 4 条短轨迹因为「唯一覆盖」被保留**，它们被别的 own 轨迹覆盖的比例是
29% / 0% / 0% / 0% —— **10 条短轨迹里有 4 条会被无条件规则错误丢弃**，
而那会丢掉一只手在那段时间的全部覆盖，不是整理计数。冗余检验挣到了它的位置。

结论：这是一次零损失的清理（轨迹数 −10%，帧 −0.00%），
**但它不改善 >2 问题（−8%），也没让任何一条录像达到「恰好 2 条」。**
所以碎片化与过计数都在中长轨迹里，不在噪声里。

## §2 ②>2 只自己的手：逐帧证据是对的，是整轨裁决覆盖了它

拿最差那条录像（`R26_0824_121025`，8.0%）把 `decisions` 和 `detect2` 对照：

```
frame 494   decisions 判 own 的 tid: 0, 3, 4
            detect2  tid 3  逐帧 own=1  p=0.9973  框宽 386
                     tid 4  逐帧 own=1  p=0.9959  框宽 152
                     tid 0  逐帧 own=0  p=0.9841  框宽 214   ← 逐帧封顶已挡掉

16 / 16 个 >2 帧在 detect2 里都恰好 3 个检测，且恰好一个 own=0
全录像 21 个三检测帧，每个都恰好有一个 own=0 —— 逐帧从没出现过 >2
```

**逐帧封顶在工作，而且它用的就是 `p`：三个候选里留分数最高的两个。**
tid 0 的 `p=0.9841` 并不低，它只是第三高。

**而 `decisions` 把它覆盖了**，因为 tid 0 是一条 192 帧的长轨迹、整轨多数票判
own，于是它的**每一帧**都被写成 own=1 —— 包括封顶挡掉的那 16 帧。

这是交付契约写明的行为：README 说「逐帧展开只是为了渲染器能直接查表，
**值是整轨一致的**：同一个 `tid` 的所有帧拿同一个判定」。

**所以 >2 既不是模型错误也不是封顶失效，是「整轨一致」这条契约与
「一个人只有两只手」这条事实冲突。**

## §3 修法与代价

对 `own` 数 >2 的帧，按逐帧 `p` 保留前 2 个。**用的是 `detect2` 里已经存在的分数，
不需要任何新模型、不需要重跑。**

```
10 条录像里 6 条有 >2 帧
要丢的 (frame, tid) 行：52 / 3117 = 1.67%
预期效果：>2 的帧按构造归零
```

| 录像 | >2 帧 | 要丢行 | 涉及轨 |
|---|---|---|---|
| R26_0824_121025 | 16 | 16 | 3 |
| R26_0826_063732 | 17 | 17 | 7 |
| R26_0825_100512 | 6 | 6 | 3 |
| R26_0824_122009 | 5 | 5 | 3 |
| R26_0824_133848 | 5 | 5 | 5 |
| R26_0824_153159 | 3 | 3 | 3 |

**代价要明写：被丢帧的轨迹会出现空洞，共 52 帧。** 在逐手身份保持（A 读法）下，
这是把「过计数」换成「覆盖空洞」—— 两者都是缺陷，但量级差 30 倍
（52 帧对 3245 帧覆盖的 1.6%），而过计数是逻辑上不可能的错误、空洞只是不完整。

**它会破坏「整轨一致」契约**，所以不能偷偷改。两个选项：

```
① decisions 保持整轨一致，另发一个 own_capped 列  → 契约不破，消费者自己选
② decisions 直接应用封顶                          → 契约改成「整轨一致，
                                                     除了同帧 >2 时按 p 截断」
```

**我倾向 ①**：契约是交付件的一部分，而渲染器和下游都按「同一个 tid 一个值」
写的。多一列的成本几乎为零，而且它让这个修正可被审计 ——
消费者能看到哪些帧被截断了。

## §4 这一轮纠正了我自己两处判断

**① 我把 >2 当成了「封顶没归零」的残余。** `cap-coupling-was-off` 记的是封顶
被一行代码关掉时有 16.5% 的帧判出 >2 只手，解耦后降到 1.3%。我因此以为
剩下的 1.3% 是封顶仍有漏洞。**实际是封顶完全正确，逐帧从没出过 >2，
是展开那一步覆盖了它。** 方向完全不同：不需要改封顶。

**② 我提议「丢掉 <10 帧的轨迹」时没想到唯一覆盖的情形。**
无条件丢会错删 4/10 条短轨迹，每一条都是某只手在那段时间的全部覆盖。
加上冗余检验之后它变成零损失，但这说明「短 = 可丢」这个直觉是错的。
