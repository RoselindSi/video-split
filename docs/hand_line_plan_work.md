# 手部线：目标改成「做出一条 work 的流水线」时的计划（2026-10-12）

取代 `docs/hand_line_plan.md` 的**目标**（那份假设目标是诊断叙事）。
两份都留着：那份的「不做的五件事」和瓶颈排序纠正仍然有效。

## §0 先把那 47 个点的差额找出来 —— 它决定这件事是不是可做的

这条线有两个数，一直被当成同一件事的两种说法，其实不是：

| 测什么 | gold | 结果 |
|---|---|---|
| **归属判断**（这只手是谁的） | 274 条轨迹 / **29 条录像** | 轨迹级 **96.6%**，自己的手误糊 **3.1%** |
| **整轨免打码**（部署出来的） | 202 条轨迹 / **10 条录像** | 放行 **49.3%**，误糊 **50.7%** |

**分类器已经 96.6%，部署出来只放行 49.3%。** 差额 47 个点，而第二个数的定义里
写着它包含四种情形（README §对人工 gold 的实测）：

```
判成 other  +  contested 弃权  +  视图不足  +  没跑到     ← 四者「结果都一样，被打码」
```

如果 96.6% 的分类器是真的，那这 47 个点里**判成 other 的那部分最多只能占
3-4 个点**，剩下 43 个点是弃权、视图不足、覆盖缺口 —— **全是工程。**

**这就是「做出一条 work 的流水线」可做的理由。** 不是去把一个 96.6% 的分类器
提到 99%，而是去把一个已经够好的判断**送达**到每一条轨迹上。

### 这件事现在就卡在一个零成本的测量上

`ownergate/against_gold.py` 第 109 行**已经**打印「被糊的原因」的分解，
但那一行的输出**从没被存下来** —— README 只记了头部数字。
所以那 38 条被误糊的 OWNER 拆成四类各多少，**我们其实不知道**。

**跑它需要 run 的 `tracks.csv`，那在服务器上，今天连接超时。**
本地只有 gold（`~/Downloads/own_gold_p{1,2,3}.csv`、`fresh_gold_p{1,2}.csv`）。

→ **Step 0（阻塞所有后续步骤）：服务器恢复后跑一次 `against_gold`，
把「被糊的原因」那一行存进 `results/`。** 一条命令，决定下面哪一条分支成立。

## §1 本地已经能算的一半：别人的手系统性更短

`frames` 列在 gold 里，所以轨迹长度不用等服务器。274 条：

| 标签 | 条数 | 中位帧 | 均值 | <10 帧 | ≥34 帧 |
|---|---|---|---|---|---|
| owner | 169 | **55** | 111.3 | 24% | 57% |
| other | 99 | **25** | 46.1 | 20% | 40% |
| ambiguous | 6 | 5 | 8.2 | 67% | 0% |

```
中位差 bootstrap（4000 次）  -56 到 -7 帧   CI 不跨零
```

**别人的手的轨迹系统性地更短。** 分布上最清楚的是两端：

```
100+ 帧    owner 36.1%   other 10.1%
10-33 帧   owner 18.9%   other 39.4%
```

这和检测器那条线对得上：别人的手中位 87px、原始召回 70.5%、过 0.60 门槛剩 43.6%
—— 检测不稳 → 轨迹短且碎 → 视图不足 / contested → 被打码。
**三个已知结果第一次连成了一条因果链，而且链条的每一环都已经单独量过。**

但注意方向：**这条链解释的是「别人的手被打码」，而那是我们想要的结果。**
它不直接解释 OWNER 被误糊。OWNER 的轨迹是更长的（中位 55 帧、57% 超过 34 帧），
所以 **OWNER 误糊的主因不太可能是碎片化** —— 这与 §0 的推断一致，
也意味着 Step 0 那个分解很可能会把大头指向 **contested 弃权**。

**这是一个可以事前写下的预测**，Step 0 一跑就能判它对不对：

> 38 条被误糊的 OWNER 里，`contested` 占最大一块，`没跑到` 与 `视图不足`
> 合计次之，`判成 other` 最小（≤ 6 条）。

预测错了比预测对了更有信息 —— 如果 `判成 other` 是大头，那 96.6% 和 49.3%
之间有一个我还没找到的不一致，必须先解决它再谈优化。

## §1b 2026-10-12 追记：Step 0 与 W1c 已执行，W1a/W1c 取消

见 `docs/hand_gate_w1c_result.md`。三件事定了：

**① Step 0 的预测命中。** 75 条 OWNER 里：判错 **6 (8%)**、弃权 **34 (45%)**、
没跑到 **9 (12%)**、放行 26 (35%)。`other` 在三条臂上都恰好是 6。
**分类器只负责 8%** —— 本文件 §0 的核心前提成立。

**② W1c 的假设被否决。** 规则（36.6% @ 泄漏 16.9%）**基本就在可达前沿上**：
同等护栏下扫六个分数列的最好阈值给 35.4%。而**零泄漏下六列全是 0.0%**，
因为顶端不可分 —— 18 条别人的手 `p_median >= 0.999`，最高那条高于全部 66 条
自己的手。**「弃权白白损失了可用性」是错的**：被弃权的轨迹，分数里本来就
没有能救它们的信息。所以 **W1a（换聚合方式）一并取消**。

**③ 真正的机制是视角被饿死，而且它可操作。**
视角数分布 `{1:68, 2:69, 3:33, 4:7}` —— **77% 只有 ≤2 个视角，而设置是 5**。
按视角分组后分数行为完全不同：`n>=3` 是**唯一**能在零泄漏下放行 OWNER 的子集
（23.5%），≤15% 护栏下给 58.8% 对全量 27.3%；`n=2` 的 OWNER 中位分是 **0.5000**
（两个视角一正一负，完全无信息），`n>=3` 跳到 0.9987。

**所以 W1b 现在是整个计划**，而且有了量化预测与事前判据。
两条限制必须一起带着：`n>=3` 只有 17 OWNER（23.5% = 4/17），
而**选择效应未检验且用手上的数据测不了**（`gold_b*` 的 frames 列是空的、
gate csv 没有帧数、服务器逐帧 csv 没有 tid）。那个混淆的检验就是 W1b 本身。

## §2 Phase W1：把弃权变成判定（预计是最大的一块）

**前提：Step 0 显示 `contested` 是主因。**

`contested` 的含义是「这条轨迹在两个视角/两次判定之间不一致，所以不敢放行」。
现在的处置是保守地打码。三条可做的，按成本排：

**W1a — 用整轨多数票代替逐帧一致性要求。**
`ownership-aggregation-rejected` 那条记忆里写着：先前否决是「对着错误参照打的分」，
**对人工 gold，P2 + 整轨多数票把暴露事件 15→0、误糊 584→286**。
也就是说这个机制已经被测过而且有效，只是当时的参照错了。
→ 先在 202 条上重跑它，这是复用已有结论不是新实验。

**W1b — contested 的轨迹补采样，而不是弃权。**
一条轨迹被判 contested 通常是视图少（`frames` 短）。
现在 `frames_per_track=5`（而且**视图数不许减**是硬规则）。
对 contested 的轨迹**单独加采样**到 9-11 个视图再判一次 ——
只对这个子集加，所以总成本是 contested 比例乘以额外视图。

**W1c — 把「不敢放行」的代价显式化。**
隐私要求是**不对称**的：漏放一只别人的手是隐私失效；误糊自己的手是**可用性**损失。
所以应该先定住护栏（别人的手被放行 = 0 或某个上界），
再看 OWNER 放行率能到多少 —— 而**这条曲线从没画过**。
现在报的是两个点（带描述 49.3%/24.4%、不带描述 37.3%/15.0%），不是曲线。
→ 用已有的 202 条分数扫阈值，画出 ROC。**零成本，只要有 run 的分数列。**

**W1 的事前判据（按录像聚类 bootstrap）：**
```
护栏不恶化 且 OWNER 放行率 CI 不跨零向上   → 采纳
两者都动                                  → 报成取舍曲线，由使用方选操作点，不默认采纳
放行率不动                                → contested 不是主因，回 Step 0 重读
```

## §3 Phase W2：覆盖缺口（「没跑到」那一块）

**前提：Step 0 显示 `没跑到` 非零。**

「没跑到」是纯工程缺陷 —— 一条 gold 轨迹在 run 的输出里根本没有对应行。
可能的原因：tid 重命名（`track_join` 的 `_tid_map.json` 没对齐）、
分片拼接丢行、某个 GPU 的那一路失败而链条没有报错。

**这一类的修复不需要判据，只需要修。** 但它需要一个**不变量检查**：

```
stage 4 输出的轨迹数  ==  stage 3b 输出的轨迹数（经 _tid_map 映射后）
```

这个检查现在不存在。**加上它，比修一次具体的缺口更有价值** ——
这个项目里「数字静默偏掉」已经发生过五次（暴露率分母、身份分组键、
封顶被关、fps/stride、删除没执行却报了成功）。

## §4 Phase W3：别人的手的召回（护栏那一侧）

只有在 W1/W2 把 OWNER 放行率推上去之后才动这里，因为它**反向**作用于护栏。

杠杆仍然是门槛不是模型（70.5% → 43.6% 丢在 0.60 门槛上，提分辨率无效，
1024/1536/1920 全是 44%）。而形状是
**低置信度框只用于「续接」不用于「新建」**：碎片端在窗口内找不到候选时
把门槛临时降到 0.35 只在那个时空窗口内找续接 —— 已有轨迹的身份不是从这一帧
推断的，所以不引入新的身份判断。

这对上 `track_join` 测到的那 **57.9% 无候选的碎片端**（而 31.8% 有唯一候选的
已经接完，碎片 321→219）。

## §5 Phase W4：那个从没跑过的冻结验证 —— 「work」的定义在这里

`ownergate/FROZEN_VALIDATION.md` 的 20-30 条全新录像、三条臂、逐轨迹配对、
按录像聚类，**判据已冻结、从没执行**。

**没有它，「它 work 了」这句话的 n 是 10。** 而且 202 条那批只有 10 条录像，
274 条那批有 29 条 —— 两个数不可比，这件事本身就说明需要一次统一口径的验证。

**可以先做一半**：在新录像上先复现 49.3%，确认那 10 条不是运气。

## §6 「work」要定成什么样，才既诚实又可达

不要定成「全自动」。现在 49.3%，而全自动需要 OWNER 放行 ≥90% 且护栏近零；
这个项目的历史里，自动决策分支**反复**没过精度闸门
（HAL ≥0.85 被拒、Driver A 九个种子下界全 <0.55、batch3 留出 0.467）。
把目标定在那里，大概率是第四次。

**可达且诚实的定义，三条同时成立：**

```
① 护栏有保证：别人的手被放行率 <= 某个事先写死的上界（例如 5%），
   在 20-30 条新录像上、按录像聚类的 CI 上界也在界内
② 可用性可量化：OWNER 放行率从 49.3% 提到 X，CI 不跨零，n >= 20 条录像
③ 代价透明：给出护栏-可用性的取舍曲线，而不是一个点
```

**这样的系统即使 X 只有 75%，也是一条 work 的流水线** —— 因为它有保证、
有量化、有曲线，使用方能据此决定操作点。而现在它只有两个点和一个
「分母是 10 条录像」的脚注。

**而 §0 的推断说 X 很可能能到 85%+：** 如果 47 个点的差额里 43 个点是
弃权与覆盖，那它们是可修的工程问题，不是需要新模型的 ML 问题。

## §7 顺序、成本、止损

```
Step 0  跑 against_gold 存下「被糊的原因」     阻塞项，需服务器，一条命令
        └─ 若「判成 other」是大头 → 停，先解决 96.6% 与 49.3% 的不一致

W1c     用已有分数扫阈值画护栏-可用性曲线       零成本（需 run 的分数列）
W1a     整轨多数票（复用已验证机制）            1-2 天
W1b     contested 子集补视图                   2-3 天，成本 = contested 比例 × 额外视图
W2      覆盖缺口 + 轨迹数不变量检查             1-2 天，不需判据
W3      低分框只用于续接                       3-5 天，反向作用于护栏，放最后
W4      冻结验证 20-30 条                      标注成本主导，可与 W1/W2 并行
```

**不做的（都已有否定实测）：** 提分辨率、扩 handness 负例、换骨干、
把 vLLM 调到贴近本地基线、在 `side` 上加闸门。

## §8 第一句话该怎么说

不是「我搭了一条流水线」，而是：

> **一个 96.6% 的归属判断，部署出来只放行 49.3%。我找出那 47 个点去了哪里，
> 并且把它们拿回来。**

这句话的前半截**现在就成立**（两个数都已测得），后半截是 W1-W4。
而它比「我做了一条 work 的流水线」更强，因为它自带一个具体的、可验证的数字缺口。
